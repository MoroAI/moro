# MoroAI remediation engineering report

Updated October 5, 2026. This report covers the implementation work begun October 3 against baseline `bac72593964c5e7218b009824f7146998b6cdfaa`, on local branch `codex/audit-remediation`. It supplements the [original audit](../../audits/2026-10-02/REPORT.md), rather than rewriting historical evidence. The [43-finding ledger](STATUS.md) records remaining acceptance criteria. [Validation](VALIDATION.md) distinguishes real execution from mocked contracts; [the runbook](RUNBOOK.md) identifies running environments.

The main result is that dangerous administration paths and fabricated pipeline outcomes have been removed or replaced with real execution. Missing models, failed training, missing evaluation evidence and unsupported deployment now produce failures. The project is still a local, single-administrator development system. This work does not establish production readiness, scientific model quality, complete offline operation, or multi-tenant security.

## 1. Administration and security boundaries

Both browser terminal endpoints now return HTTP 410. They cannot interpret arbitrary command strings, even for an authenticated administrator. Typed APIs remain available. Docker actions require a managed-container label and a validated container ID; the Compose web services have no Docker socket mount. This removes the original unauthenticated shell-execution path and reduces the consequences of a browser-origin attack.

Dashboard and gateway share authentication middleware. A private installation-token file or configured token grants administrative access; browser login issues an eight-hour signed, HttpOnly, SameSite=Strict cookie. Host validation and exact origin checks, including ports, apply to HTTP and WebSocket traffic. Cookie-authenticated mutations require same-origin requests. Tokens are generated without publishing an empty intermediate file and rejected if their file permissions are not private. Request limits check both declared length and bytes received. Source: [security middleware](../../../src/moro/dashboard/security.py), [system API](../../../src/moro/dashboard/api/system.py), [boundary tests](../../../tests/test_security_boundaries.py).

These are meaningful local controls, with explicit limits. There are no per-user roles, scoped API keys or tenant boundaries. Cookie security depends on HTTPS when remotely deployed. CSP still permits inline script and evaluation for existing UI dependencies. Rate limits, concurrency quotas, disk quotas and account-level auditing remain unimplemented. A local administrator capable of changing project files, database records or process environment remains trusted. Filesystem checks are not a sandbox against a hostile operating-system administrator.

Uploads receive generated storage names instead of trusting client filenames. Files are streamed with a 10 MiB limit, restricted formats and content validation, and exclusive/no-follow publication. Multi-file requests are capped at 20. Traversal, overwrite, malformed content and symlink cases have regression coverage. Dataset previews are limited to 100 rows, though counting/verifying large files still has an I/O cost. Source: [uploads](../../../src/moro/dashboard/uploads.py), [dataset API](../../../src/moro/dashboard/api/datasets.py).

Analytics no longer accepts caller-controlled SQL expressions as identifiers. Config writes validate strict schema before changing disk, require an ETag precondition and use locked atomic replacement. JSON Schema scoring cannot retrieve arbitrary external references. The Git hook inspects staged blob bytes, including tests, rather than the potentially different working-tree file. Full PEM private-key blocks are redacted, including unterminated blocks. These controls address concrete reproductions; they are not a complete secret or PII detector.

The webhook now requires a long API key, rejects browser-origin ingestion, limits body/batch sizes and validates ratings. A stable idempotency key is bound to sender identity and payload digest. Insertion and replay recording occur in one transaction; identical replay returns the original result, while changed content with the same key returns 409. Health reveals only liveness, not production records. Live HTTP verification exercised these cases against native and Compose receivers. Source: [receiver](../../../src/moro/flywheel/webhook/receiver.py).

## 2. Dataset identity, privacy and leakage

The SDK compiler now delegates to the same real compiler as the CLI. Missing data fails; no sample is silently manufactured and no raw source is copied into all three splits. Immutable dataset versions contain normalized data, distinct split files, reports, rejection metadata and a hash inventory. Build identity incorporates source bytes, relevant configuration, glossary bytes and compiler implementation hashes. Inputs are rechecked before publication, and absolute/relative references to the same source agree. Source: [compiler](../../../src/moro/data/compiler.py), [versioning](../../../src/moro/data/versions.py), [shared build service](../../../src/moro/cli/data.py).

Split assignment groups normalized identical content even when deduplication is disabled. Optional document/session grouping uses explicit `metadata.group_id`, and missing group IDs fail rather than silently fragmenting a document. Sorting group identities before seeded assignment makes membership insensitive to input ordering. Ratios apply to groups, so differently sized groups may produce different row proportions. Semantic near duplicates across distinct groups still require analysis; grouping is not proof that an evaluation set is uncontaminated. Source: [splitter](../../../src/moro/data/splitter.py), [version/split tests](../../../tests/test_dataset_versions.py).

Row provenance survives normalization and scoring. Unknown factual grounding, coherence, authority and vector density are null, not fabricated perfect or midpoint scores. Explicit privacy actions support flag, redact, reject and quarantine; the default **flag** policy retains detected content. Rejection evidence avoids duplicating raw rejected records. These are policy mechanisms, not a claim of comprehensive anonymization. Regex recall must be measured on realistic languages and secret formats.

Compiled versions now have verified previews. A modified snapshot returns 409; raw-data deletion and compilation APIs explicitly reject immutable versions. This protects the files referenced by training records and resolves the listed-version/404-preview mismatch. It does not implement retention or garbage collection.

Scientific gaps remain substantial: quality scoring is heuristic, threshold calibration is absent, actual tokenizer/template lengths are not used throughout compilation, large inputs are substantially memory resident, and document/OCR/table-to-supervision workflows are not implemented. The project must not claim that these heuristics guarantee zero knowledge loss. The next useful evaluation is a labeled corpus with rare facts, duplicates, contradictions, multilingual examples and jargon spam, compared against simple baselines on a sealed holdout.

## 3. Real training and bounded recovery

CLI, SDK, async adapter and runtime orchestration now share the real training service. Supplied fake metrics/steps are rejected. Dataset version identity and the actual run ID flow through downstream phases. Missing optional dependencies or model files cause failure, not a simulated successful run. Failed pending/running records are marked failed. A per-project interprocess lock prevents overlapping training through these entry points. Source: [training service](../../../src/moro/cli/train.py), [SDK runner](../../../src/moro/training/runner.py), [lock](../../../src/moro/training/locking.py).

The backend passes weight decay and records adapter settings, sequence length and seed from the correct configuration sections. Memory planning uses one shared heuristic and preserves unknown model sizes instead of inserting a favorable default. Special-case benchmark answers were removed. The estimator is explicitly uncalibrated; monotonic response to batch/sequence changes is a consistency property, not measured prediction accuracy.

OOM recovery performs at most one backend restart. It reduces the microbatch while compensating gradient accumulation, or enables checkpointing where appropriate. It does not silently shrink the sequence or adapter architecture. The failed trainer/model references and exception scope are cleared before rebuilding, and requested/effective configs are preserved. The runtime also bounds its own recovery. Source: [Hugging Face backend](../../../src/moro/training/hf_backend.py), [runtime](../../../src/moro/runtime/orchestrator.py).

Three real CPU integration cases construct a tiny local GPT-2 model and tokenizer, execute one SFT step, save adapters, reload them and generate. SDK cases also compile data, persist real evaluation and create a gated release. Network socket connections are blocked during the integration. The recovery case injects one controlled OOM-shaped exception on CPU and uses a weak reference to ensure the failed trainer is collected before the real retry. This proves a reference-lifetime property and successful CPU recovery, **not** actual CUDA memory reclamation. Source: [CPU integration](../../../tests/integration/test_training_cpu.py).

Cancellation and resume remain incomplete. `asyncio.to_thread` cannot terminate the backend when its awaiter is cancelled. The API therefore rejects unsupported stop/cancel requests instead of announcing that training stopped. A durable worker architecture must own a process group, job/attempt IDs, leases, heartbeat, checkpoints and device admission. It must demonstrate termination of only the owned process and correct restart reconciliation before these features are advertised.

## 4. Evaluation, release and serving truthfulness

The evaluation harness executes the real inference/scoring runner and persists evidence. Unknown runs and missing suites fail. A measured zero remains zero in APIs and model listings. Strict robustness no longer rewards consistent wrong answers, and empty measurements cannot receive an A grade. Negation/entity swaps can change the correct answer; they are excluded from default automatic evaluation and exported for label review without reusing the old oracle. Source: [harness](../../../src/moro/eval/harness.py), [robustness](../../../src/moro/eval/robustness.py), [model API](../../../src/moro/dashboard/api/models.py).

SDK release requires a completed recorded run and the real gate; caller-supplied favorable scores cannot substitute for evidence. Bundles are staged under a lock, adapter bytes are checked against the gated digest, and publication is atomic without overwriting an existing release. Ollama conversion/deployment also binds to the evaluated adapter digest. GGUF script arguments are validated/quoted and execution is bounded. Source: [release manager](../../../src/moro/release/manager.py), [Ollama export](../../../src/moro/export/ollama.py), [GGUF export](../../../src/moro/export/gguf.py).

The integration gate intentionally uses a zero minimum pass rate with safety gating disabled to test the mechanics of publishing a real, known-failing evaluation. Its successful release is **not model-quality evidence**. Comparative release gates remain fail-closed. Base weights/revision, tokenizer/template, decoding/runtime and transformed binaries need stronger identity binding and post-conversion testing. Hash inventories establish integrity, not publisher authenticity; signing/trust roots and attestation verification are still absent.

Unsupported SDK/dashboard deployment now fails explicitly. Model promotion selects a recorded release; it does not pretend that a server is running. The gateway forwards the full conversation and options to Ollama, reports its actual inventory and measured token counts, and returns upstream failures without inventing assistant text. The live Ollama inventories are empty: missing-model failure was verified; successful live inference was not. Mocked unit tests cover forwarding and success-response mapping. Source: [gateway](../../../src/moro/dashboard/gateway.py), [deployment API](../../../src/moro/dashboard/api/deployment.py).

## 5. Feedback integrity and learning limits

Undersized extraction batches retain pending input. Capped batches acknowledge only source IDs actually persisted. Pair IDs are deterministic, epoch files are created exclusively, and database insertion plus acknowledgement happens transactionally. Reusing an epoch fails before overwriting existing output. Normal exception rollback removes only the newly created owned file. A hard crash can still leave an orphan; automatic reconciliation is not implemented. Source: [flywheel orchestrator](../../../src/moro/flywheel/orchestrator.py).

The default extractor uses explicit human corrections. Rating-derived synthetic preferences are opt-in and marked unreviewed. A correction can itself be malicious or wrong; authenticity, review and poisoning defenses remain required. Extracted state is distinct from trained state, trainer failure prevents deployment, and deployment requires explicit enablement plus a gate. The project still lacks a completed DPO training/review loop and must not present pair extraction as measured alignment improvement.

## 6. Distribution, dependencies and development environments

Docker now installs after copying source, uses a nonroot account and serves from a project workspace. Compose publishes localhost ports and starts the actual webhook ASGI app. Browser assets and the Git hook ship in the wheel; an isolated installed-wheel smoke test runs outside the checkout. CI includes evaluation extras and a dedicated real CPU training job. Release publishing failures are no longer ignored; local validation does not claim a remote CI or registry publish occurred.

The Linux reference training stack was upgraded and pinned, then exercised with real CPU training. Its Python advisory scan found zero known matches; the CPU Torch local-version suffix required a separate normalized-version scan. See exact versions and scan limitations in [validation](VALIDATION.md). The [PyTorch deserialization advisory](https://github.com/pytorch/pytorch/security/advisories/GHSA-63cw-57p8-fm3p) and [PyTorch security policy](https://github.com/pytorch/pytorch/blob/main/SECURITY.md) reinforce why a version upgrade is not a safe-loading guarantee for untrusted model artifacts. Advisory absence is not proof of vulnerability absence.

Both native and Compose development services are running against a synthetic scratch project, with localhost bindings. No real model was downloaded into Ollama. The old audit CPU system environment remains present and must not be confused with the verified `/opt/moro-candidate` environment. CUDA/MPS, optional feedback automation, real merge/conversion, production serving and full authenticated browser interaction are not verified. The browser automation displayed the login page but did not send a login POST; HTTP login/session/dashboard behavior passed independently.

## 7. Next implementation sequence and acceptance

1. **Durable execution:** introduce a persistent job/attempt state machine and an owned subprocess worker. Prove restart recovery, one device lease, cancellation, failed-heartbeat handling and exact checkpoint compatibility with fault injection. Keep HTTP requests separate from long-running training.
2. **Evidence and publication:** persist complete base/tokenizer/template/decode/runtime identities; require compatible paired evaluations for regression gates; reevaluate final merged/quantized artifacts. Route all publication through the same gate and digest checks.
3. **Dataset and preference trust:** tokenizer-aware lengths and explicit target-preserving truncation, streaming builds, cross-split similarity reports, labeled quality/PII benchmarks and reviewed corrections. Add document extraction only with source-span provenance and tested supervision generation.
4. **Operational security:** scoped actor credentials, TLS deployment, quotas, retention/deletion, encrypted backups and restore drills. Add dependency locks, browser/container advisory checks, SBOMs and signed attestations with a verification policy.
5. **Serving:** implement backend ownership/readiness, real successful inference probes, quality checks, rollback and deletion of only owned resources. Promotion must never substitute for deployment readiness.

These are independent deliverables with testable outcomes. The ledger leaves them open instead of treating removal of false-success behavior as implementation of the missing capability.
