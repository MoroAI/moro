## Version
**v0.1 — Architectural Foundation**

## Working Name
- **Brand:** MoroAI

- **CLI command:** `moro` or fallback `moroai`

---

# 1. Executive Summary

MoroAI is a **local-first model adaptation foundry**.

Its purpose is to help engineers and teams turn **private, messy, domain-specific data** into **reliable, deployable local language models** under real-world constraints such as:

- limited GPU memory
- privacy requirements
- noisy datasets
- lack of ML expertise
- weak evaluation practices
- deployment friction
- reproducibility problems

MoroAI is not just a fine-tuning script generator.

It is a system that manages the full lifecycle:

```text
raw data
→ normalized dataset
→ memory-safe training recipe
→ trained model
→ evaluated model
→ approved release
→ local deployment
→ feedback loop
→ improved model
```

The core product should feel like this:

```bash
moro init
moro import ./raw/support_docs
moro data build
moro doctor
moro recipe suggest
moro train
moro eval run
moro release create v0.1.0
moro deploy --target ollama
```

That is the experience MoroAI should optimize for.

---

# 2. The Wicked Problem MoroAI Solves

The real problem is not simply:

> “How do I fine-tune a model with low VRAM?”

The deeper problem is:

> **How can a team safely, reproducibly, and affordably convert private data into a trustworthy local model that can be evaluated, released, and improved over time?**

This is wicked because:

1. Data is messy and private.
2. Hardware is constrained.
3. Model quality is hard to measure.
4. Training configurations are fragile.
5. Deployment is still manual.
6. Teams need auditability.
7. Model behavior can regress.
8. Feedback loops are usually missing.

MoroAI should solve the whole loop, not just one stage.

# 5. Core Design Principles

These principles should guide every implementation decision.

---

## Principle 1: Local-first by default
MoroAI should work without requiring cloud services.

Cloud may be optional later, but the core product must work locally.

---

## Principle 2: Recipes over raw configuration
Users should not need to become ML experts.

MoroAI should provide safe, hardware-aware recipes.

---

## Principle 3: Trust is a first-class feature
Evaluation, safety checks, provenance, and model cards are not optional extras.

They are part of the core platform.

---

## Principle 4: Reproducibility by design
Every run should be reproducible from:
- config
- dataset version
- code version
- dependency versions
- hardware profile

---

## Principle 5: Small models are first-class citizens
MoroAI should specialize in:
- 0.5B
- 1B
- 1.5B
- 3B
- 7B
- 8B class models

with strong support for consumer and workstation hardware.

---

## Principle 6: The CLI is the product surface
Start with a beautiful CLI.

GUI can come later.

---

## Principle 7: Wrap proven engines first
Do not start by building a custom training engine.

Wrap:
- Hugging Face Transformers
- PEFT
- TRL
- bitsandbytes
- Accelerate
- optionally Unsloth

Then innovate later.

## A. Control Plane

### Responsibilities
- manage projects
- register datasets
- version dataset snapshots
- store recipes
- track runs
- store eval results
- manage artifacts
- manage releases

### Components
- Project Manager
- Dataset Registry
- Recipe Registry
- Run Tracker
- Eval Registry
- Artifact Registry
- Release Manager

---

## B. Execution Plane
This is where work happens.

### Components
1. **Data Compiler**
   - ingestion
   - normalization
   - cleaning
   - deduplication
   - quality scoring
   - splitting

2. **Training Runner**
   - loads model
   - applies adapter/quantization
   - executes training
   - saves checkpoints

3. **Evaluation Runner**
   - runs eval suites
   - scores outputs
   - compares base vs tuned

4. **Export/Release Runner**
   - exports adapters
   - merges weights
   - builds GGUF/Ollama packages
   - writes model cards

---

## C. Intelligence Plane
This makes MoroAI feel smart.

### Components
1. **Recipe Engine**
   - suggests hardware-safe training configs

2. **Memory Governor**
   - estimates VRAM
   - tunes settings
   - handles OOM recovery

3. **Diagnostics Engine**
   - explains failures
   - suggests fixes
   - identifies dataset issues

---

## D. Backend Adapter Plane
This isolates external dependencies.

### Training adapters
- Hugging Face backend
- PEFT backend
- optional Unsloth backend
- experimental streaming backend later

### Deployment adapters
- Ollama

# 15. Recipe Engine Architecture

The Recipe Engine turns constraints into safe training settings.

---

## Inputs
- GPU vendor
- VRAM
- CPU RAM
- disk space
- target model
- dataset size
- max sequence length desired
- quality target
- latency target

## Outputs
- recommended model
- quantization mode
- adapter settings
- batch size
- gradient accumulation
- optimizer
- sequence length
- gradient checkpointing
- offload strategy

---

## Example recommendation output

```text
Recommended recipe:
- model: Qwen/Qwen2.5-1.5B-Instruct
- quantization: nf4
- adapter: lora
- lora_r: 16
- target_modules: q_proj,k_proj,v_proj,o_proj
- max_seq_length: 1024
- batch_size: 1
- gradient_accumulation_steps: 16
- optimizer: paged_adamw_8bit
- gradient_checkpointing: true
Estimated peak VRAM: 5.1 GB
Confidence: high
```

---

## Recipe engine levels

### Level 1: Rule-based presets
Best for MVP.

Examples:
- `<4GB`: 0.5B–1B, 4-bit, seq 512
- `6GB`: 1B–1.5B, 4-bit, seq 1024
- `8GB`: 1.5B–3B, 4-bit, seq 1024
- `12GB`: 3B, 4-bit, seq 2048
- `24GB`: 7B–8B, 4-bit, stronger settings

### Level 2: Profiler-assisted tuning
Run a tiny profiling step and measure memory.

### Level 3: Auto-recovery
If OOM occurs:
1. reduce max sequence length
2. reduce batch size
3. reduce adapter targets
4. enable stronger offload
5. retry

# 18. Evaluation Engine Architecture

This is what makes MoroAI trustworthy.

---

## Core idea
Every tuned model should be evaluated against:
- a base model
- previous tuned versions
- domain-specific golden cases

---

## Eval suite structure

```yaml
name: support-golden-v1
domain: support
cases:
  - id: case_001
    input:
      messages:
        - role: user
          content: "How do I reset my password?"
    expect:
      contains:
        - "Settings"
        - "Security"
    scorers:
      - contains
      - tone
      - helpfulness
```

---

## Scorer types

### Deterministic scorers
- exact match
- contains
- regex
- JSON schema validity
- field extraction accuracy

### Model-based scorers
- helpfulness
- tone
- faithfulness
- safety
- pairwise comparison

### Performance scorers
- latency
- peak memory
- tokens/sec

---

## Evaluation reports

Each eval run should produce:

```text
Base score: 58.3
Tuned score: 76.9
Improvement: +18.6

Category breakdown:
- correctness: +21%
- tone: +9%
- hallucination: -7%
- safety: pass
```

---

## Release gates

Example:

```yaml
release:
```

# 26. Key Architectural Decisions

## ADR 1: Build a modular local CLI first
Not a web app.

Reason:
- fastest path to real utility
- easier to test
- better for engineers

---

## ADR 2: Use Python for the core
Reason:
- ML ecosystem alignment
- faster integration with HF/PEFT

---

## ADR 3: Wrap existing training libraries before building custom engine
Reason:
- reduces risk
- speeds delivery
- leverages proven code

---

## ADR 4: Make evaluation first-class early
Reason:
- quality proof is a major differentiator

---

# 30. Major Risks and Mitigations

## Risk 1: Name conflicts
Mitigation:
- check GitHub/PyPI/domain/trademark early
- use MoroAI as brand, Moro as product

## Risk 2: Training fragility across hardware
Mitigation:
- conservative defaults
- doctor checks
- auto-recovery recipes

## Risk 3: Eval quality is hard
Mitigation:
- start with simple golden suites
- add deterministic checks first
- use model-based judging carefully

## Risk 4: Data privacy issues
Mitigation:
- local-only default
- PII scanning
- no telemetry by default

## Risk 5: Scope creep
Mitigation:
- ship CLI MVP first
- delay GUI and custom engines
