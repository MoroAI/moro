# 10. The three architectural planes in detail

## A. Control Plane

This manages the state of the system.

### Components

- Project manager

- Dataset registry

- Recipe registry

- Run tracker

- Eval registry

- Artifact registry

- Release manager

### Storage choices

- **SQLite** for metadata

- **DuckDB** for analytics and dataset profiling

- filesystem for artifacts

### Why this matters

MoroAI must be:

- local-first

- reproducible

- auditable

- easy to install

- not dependent on heavy infrastructure

SQLite + DuckDB is a very strong choice.

---

## B. Execution Plane

This performs the actual work.

### 1. Data Compiler

Transforms raw inputs into clean training-ready datasets.

Functions:

- ingest JSONL/CSV/Markdown/text

- normalize into chat/instruction format

- deduplicate

- filter bad rows

- score quality

- split train/validation/eval

- detect PII

This is critical.

---

### 2. Training Runner

Wraps the training backend.

Responsibilities:

- load model

- apply quantization

- apply LoRA/QLoRA

- monitor memory

- checkpoint

- save adapter

- log metrics

At first:

- wrap Hugging Face + PEFT + bitsandbytes

Later:

- Unsloth backend

- experimental memory backend

---

### 3. Evaluation Runner

Runs eval suites and compares models.

Functions:

- load base model

- load tuned model

- run prompts

- score outputs

- generate comparison report

- gate releases

---

### 4. Export / Release Runner

Packages the model for deployment.

Functions:

- export adapter

- merge weights

- generate GGUF

- create Ollama Modelfile

- write model card

- version release

---

## C. Intelligence Plane

This is where MoroAI becomes more than a script.

### 1. Recipe Engine

Suggests the best training recipe based on:

- hardware

- dataset size

- target quality

- latency constraints

- privacy constraints

### 2. Memory Governor

Prevents OOMs and optimizes memory use.

### 3. Diagnostics Engine

Explains failures and recommends fixes.

This is the “smart” layer.

# 18. The Memory Governor design

This should be a first-class subsystem.

## Inputs

- GPU VRAM

- CPU RAM

- model architecture

- quantization method

- dataset token distribution

- desired max sequence length

- target quality

- time budget

## Outputs

- recommended model

- quantization

- adapter rank

- target modules

- batch size

- gradient accumulation

- optimizer

- checkpointing

- offloading

- packing settings

---

## Algorithm strategy

### Level 1: Rule-based engine

This is enough for MVP.

Examples:

- if VRAM < 4GB → 0.5B–1B model, 512 seq, 4-bit

- if VRAM 6GB → 1.5B model, 1024 seq

- if VRAM 12GB → 3B model, 2048 seq

- if VRAM 24GB → 7B model with stronger settings

### Level 2: Profiler-assisted search

Run a tiny profile step:

- load model

- run one forward/backward pass

- measure peak memory

- adjust config automatically

### Level 3: Recovery engine

If OOM occurs:

- reduce seq length

- reduce batch

- reduce adapter targets

- enable stronger offload

- retry safely

This makes MoroAI feel robust.
